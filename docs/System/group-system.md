# Group System

User-facing group management documentation belongs in [`../UserApp/access-control.md`](../UserApp/access-control.md).

## 1. Purpose

The Group System represents where users belong within the single organization managed by a NexGestion installation. A group may represent a department, branch, store, project team, or working group.

Groups do not grant access based on their name, type, membership, or hierarchy. Roles answer **what a user may do**; groups answer **where a user belongs**. All request authorization comes from roles.

Group data is owned by UserSystem and stored in `user.db`.

## 2. Group Kinds

Every group has one of two kinds:

| Kind | Hierarchy | Purpose |
| --- | --- | --- |
| `organization` | May have one parent organization group | Represents the reporting structure used to resolve a user's manager |
| `project` | No parent | Represents temporary or cross-functional work and never participates in leave approval |

The stored `type` field is restricted to these two values. Department, branch, team, and similar descriptions belong in the group's name or a future optional category field; they are not separate approval semantics.

An organization hierarchy is ordered from lower groups to higher groups using `parent_group_id`. For example:

```txt
Level 1 — Company
└── Level 2 — Taiwan Region
    └── Level 3 — Technology Division
        └── Level 4 — Engineering Department
            └── Level 5 — Platform Team
```

Project groups are flat. An organization group cannot have a project parent, and a project group cannot have children.

### 2.1 Organization levels

Organization groups use exactly five available hierarchy levels. Level numbers run from the highest authority to the most specific operating group:

| Level | Position | Typical examples | Valid parent |
| --- | --- | --- | --- |
| `1` | Highest organization authority | Company, legal entity | None |
| `2` | Major organizational area | Region, business group | Active level 1 organization |
| `3` | Division | Division, business unit | Active level 2 organization |
| `4` | Department | Department, branch | Active level 3 organization |
| `5` | Operating team | Team, store, section | Active level 4 organization |

The examples are descriptive only; approval behavior is determined by the numeric level rather than the group's name.

Level rules:

- `organization_level` is required for an organization group and must be an integer from `1` through `5`.
- Level 1 is the root level and must not have a parent.
- Levels 2 through 5 require exactly one parent at the immediately preceding level.
- A hierarchy cannot skip levels. A level 5 group, for example, cannot be attached directly to level 3.
- A child must always have a numerically greater level than its parent.
- Changing a group's level or parent must keep its entire descendant tree valid.
- Multiple level 1 roots are permitted when one installation manages separate legal entities.
- Project groups have no `organization_level`; the stored value must be `NULL`.
- A user can be a member of organization groups at several levels, but exactly one active membership is marked as their primary organization membership.

## 3. Data Model

### 3.1 `groups`

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `id` | TEXT/UUID | Yes | Immutable identifier generated by the server |
| `name` | TEXT | Yes | Human-readable name, unique case-insensitively |
| `type` | TEXT | Yes | `organization` or `project` |
| `organization_level` | INTEGER | Conditional | Required level `1`–`5` for an organization group; `NULL` for a project |
| `parent_group_id` | TEXT/UUID | No | Parent organization group; valid only for an `organization` group |
| `status` | TEXT | Yes | `active` or `inactive`; defaults to `active` |
| `created_at` | DATETIME | Yes | Creation time in UTC |
| `updated_at` | DATETIME | Yes | Last update time in UTC |

### 3.2 `user_groups`

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `user_id` | TEXT/UUID | Yes | Assigned user |
| `group_id` | TEXT/UUID | Yes | Assigned group |
| `title` | TEXT | No | User's title within this group |
| `joined_at` | DATETIME | No | Membership start time |
| `left_at` | DATETIME | No | Membership end time; `NULL` means active |
| `is_primary_organization` | BOOLEAN | Yes | Identifies the one organization membership used as the user's reporting line |
| `created_at` | DATETIME | Yes | Record creation time |

The composite `(user_id, group_id)` key prevents duplicate membership records. A user may belong to multiple groups and projects, but may have at most one active primary organization membership. Project memberships can never be primary organization memberships.

### 3.3 `group_roles`

Each group owns exactly two generated system roles:

| Kind | Generated title | Purpose |
| --- | --- | --- |
| `manager` | `<Group Name> Manager` | Records manager membership; API access still requires catalog permissions |
| `member` | `<Group Name> Member` | Records ordinary membership without management authority |

Membership updates keep `user_groups` and the corresponding `user_roles` assignment synchronized. A user has only one of these two roles for a given group at a time.

## 4. Hierarchy Rules

- A group may have no parent or one existing parent group.
- A group cannot be its own parent.
- Updating a parent must not create a direct or indirect cycle.
- An unknown parent ID is rejected.
- A group with child groups cannot be deleted until its children are moved or deleted.
- Clearing a parent through the current PATCH contract uses an empty `parent_group_id` string.
- Only active `organization` groups participate in the hierarchy.
- An `organization` group's parent must also be an active `organization` group.
- A `project` group must not have a parent or child.
- A level 1 organization has no parent; every level 2–5 organization has a parent whose level is exactly one less.

The service traverses the proposed ancestor chain before saving an update, preventing structures such as `A → B → A`.

## 5. Manager Resolution

Leave approval uses the requester's primary organization membership and ignores all project memberships.

The approver is resolved in this order:

1. Start at the requester's primary organization group.
2. Select active managers of that group, excluding the requester.
3. If the requester is an ordinary member and an eligible manager exists in that group, assign those managers.
4. If the requester is a manager of that group, do not assign their peer managers at the same level; move to the parent level.
5. If no eligible manager exists, move to the parent organization group and repeat.
6. Continue upward one level at a time, ending at level 1.
7. If no eligible higher manager exists, assign the request to an administrator.

Example:

```txt
Requester                         Approval destination
Level 5 Platform Team member  -> Level 5 Platform Team manager
Level 5 Platform Team manager -> Level 4 Engineering Department manager
Level 4 Department manager    -> Level 3 Division manager
Level 3 Division manager      -> Level 2 Region manager
Level 2 Region manager        -> Level 1 Company manager
Level 1 Company manager       -> Administrator
```

If an intermediate group has no active manager, routing continues to the next parent. The request is never routed downward, sideways to a sibling group, or through a project group.

An administrator is an active protected user or an active user whose role grants all permissions. The requester can never approve their own leave, including through administrator fallback. If no other eligible administrator exists, the request remains pending and is flagged `requires_assignment`.

When several managers are eligible at the same hierarchy level, all receive the approval task and the first valid decision completes it. Later decisions are rejected as a state conflict.

Manager resolution is snapshotted when the request is submitted. Membership or hierarchy changes do not silently alter an existing approval assignment. An administrator may explicitly reassign a pending request, and every assignment change must be audited.

Being a group manager provides only record-scoped eligibility to decide leave requests assigned to that manager. It does not grant unrelated API permissions or bypass the Role System.

## 6. Validation and Business Rules

- The server generates group IDs.
- Names and types are trimmed and must not be empty.
- Names are unique using case-insensitive database comparison.
- Status defaults to `active` and accepts only `active` or `inactive`.
- Group list results are ordered by name case-insensitively.
- `member_count` counts memberships whose `left_at` is `NULL`.
- Existing memberships do not block deletion; they are removed atomically with the group.
- Group creation and creation of its Manager and Member roles occur in one transaction.
- Generated group roles are protected from direct Role API updates and deletion.
- Renaming a group atomically renames its generated Manager and Member roles.

The protected initial administrator always has access. Other users may create, update, or delete groups when their effective permissions include `groups.manage`.

## 7. API Contract

All group endpoints require a valid access token.

| Method | Path | Current authorization | Description |
| --- | --- | --- | --- |
| `GET` | `/api/groups` | `groups.read` | List groups |
| `GET` | `/api/groups/{id}` | `groups.read` | Read one group |
| `POST` | `/api/groups` | `groups.manage` | Create a group |
| `PATCH` | `/api/groups/{id}` | `groups.manage` | Update a group |
| `DELETE` | `/api/groups/{id}` | `groups.manage` | Delete a leaf group and its owned records |
| `GET` | `/api/groups/{id}/members` | `groups.read` | List active members |
| `PUT` | `/api/groups/{id}/members/{userId}` | `groups.assign` | Add or update a member |
| `DELETE` | `/api/groups/{id}/members/{userId}` | `groups.assign` | Remove a member |

Create request:

```json
{
  "name": "Finance",
  "type": "organization",
  "organization_level": 4,
  "parent_group_id": "a08e17ba-39ff-4505-92aa-a2a0b6c267f8",
  "status": "active"
}
```

`name` and `type` are always required. `organization_level` is also required when `type` is `organization`. Update request fields are optional, but the resulting group must still satisfy all level and parent constraints.

Group response:

```json
{
  "id": "dcbcb1a3-e042-44a4-8b7c-d476b299ab57",
  "name": "Finance",
  "type": "organization",
  "organization_level": 4,
  "parent_group_id": "a08e17ba-39ff-4505-92aa-a2a0b6c267f8",
  "status": "active",
  "created_at": "2026-07-22T08:30:00Z",
  "updated_at": "2026-07-22T08:30:00Z",
  "member_count": 0,
  "manager_role_id": "382c962e-8de2-4beb-9240-23859155f43d",
  "member_role_id": "f628773e-a017-445d-9a2f-5bfc75d87646"
}
```

List responses wrap records in a `groups` property. Creation returns `201 Created` with a `Location` header; successful deletion returns `204 No Content`.

Add or update member request:

```json
{
  "role": "manager",
  "title": "Branch Manager",
  "joined_at": "2026-07-22T08:30:00Z"
}
```

`role` accepts `manager` or `member` and defaults to `member`. Repeating the request updates the existing membership and replaces its group role. Omitting `joined_at` uses the current UTC time.

Member response:

```json
{
  "user_id": "94abfdad-4800-49f8-a75f-6779e53a546d",
  "display_name": "Mina Lin",
  "email": "mina@example.com",
  "role": "manager",
  "title": "Branch Manager",
  "joined_at": "2026-07-22T08:30:00Z"
}
```

Member-list responses wrap records in a `members` property.

## 8. Error Responses

| Status | Condition |
| --- | --- |
| `400 Bad Request` | Missing name/type, invalid status, invalid parent, or hierarchy cycle |
| `401 Unauthorized` | Missing or invalid authentication |
| `403 Forbidden` | Authenticated user is not currently allowed to manage groups |
| `404 Not Found` | Group does not exist |
| `409 Conflict` | Duplicate name, or group has child groups |

Errors use the shared JSON form:

```json
{
  "error": "group not found"
}
```

## 9. Frontend

Group management is available under **Settings → Access Control → Groups**. The list displays name, type, parent, status, active member count, and available actions. The detail screen supports metadata editing and membership management according to the user's role permissions.

## 10. Audit and Security

Create, update, delete, and membership API operations write request-log events containing immutable record IDs.

The router authenticates all group requests. Reads enforce `groups.read`, mutations enforce `groups.manage`, and membership changes enforce `groups.assign`. Group membership and generated group roles do not bypass request permissions.

## 11. Deletion Policy

Generated Manager and Member roles are owned by their group. They cannot be deleted from the Role API and must not survive after their group is deleted.

Deleting a leaf group performs this transaction in order:

1. Remove every user's assignments to the generated Manager and Member roles.
2. Remove all `user_groups` membership records for the group.
3. Remove both `group_roles` ownership links.
4. Delete the generated Manager and Member roles.
5. Delete the group.

Users themselves are never deleted or disabled. Their unrelated custom roles, other group roles, and other memberships remain unchanged. If any step fails, the transaction rolls back, leaving the group and all relationships intact.

A group with children cannot be deleted because silently deleting or moving an organizational subtree is ambiguous. The administrator must first delete the children or assign them a different parent.

| Record | Independent deletion | Owner-driven deletion |
| --- | --- | --- |
| Group | Allowed only when it has no children | Removes memberships and generated roles |
| Group Manager role | Not allowed | Deleted with its group |
| Group Member role | Not allowed | Deleted with its group |
| Group membership | Requires `groups.assign` | Deleted with its group |

## 12. Explicitly Unsupported Behavior

Permission inheritance from groups is intentionally unsupported. Parent relationships describe organization structure only.

The broader identity and authorization model is documented in [`user-system.md`](./user-system.md).
