# Inventory implementation

The standalone inventory module is available at `/inventory/stock`. It owns `inventory.db`, initialized with one active Main warehouse. Existing installations receive the schema at startup. No business data is migrated from other modules.

## Implemented

- Warehouses and optional storage locations, including active/inactive status.
- Items with unique SKU, unit of measure, and optional unique barcode.
- Dedicated receiving and shipping routes and navigation entries. Keyboard-wedge barcode scanners submit codes with Enter; barcode lookup takes precedence over SKU. Manual item selection is also available.
- Multi-line receipts and shipments, warehouse/location transfers, and signed adjustments.
- Outbound states: pending → packed → shipped, pending → shipped, and cancellation before shipping. Only shipping deducts stock. Pending shipments do not reserve stock.
- Stock derived from an append-only movement ledger; exact quantities to six decimal places. Insufficient stock is rejected per item, warehouse and location. Unassigned stock is a separate location bucket.
- Transactional operations, including transfers and multi-line stock checks. Repeated shipment transitions cannot deduct stock twice.
- Record history with actor, date, timestamp, quantities, notes and tracking reference.

## Permissions

Assign `inventory.access` to enter the screens, `inventory.read` to read data, and `inventory.manage` to change master data and record movements. Protected administrators have access automatically. Inventory screens use the real authenticated API in both development and production. Because the existing development authentication provider uses mock users, use a production build with real login for end-to-end inventory use.

## API

All endpoints require authentication and the corresponding read or manage permission.

| Method | Path | Result |
| --- | --- | --- |
| GET | `/api/inventory/warehouses`, `/locations`, `/items` | Entity arrays |
| POST | Same entity paths | Create entity |
| PUT | Same entity paths + `/{id}` | Save entity |
| GET | `/api/inventory/scan?code=...` | Item, barcode first then SKU |
| GET | `/api/inventory/stock` | Per-item, warehouse and location balances |
| GET | `/api/inventory/movements` | Signed append-only ledger entries |
| GET | `/api/inventory/records` | Receipts, shipments, transfers and adjustments |
| POST | `/api/inventory/records` | Create operation atomically |
| PATCH | `/api/inventory/records/{id}` | Transition shipment using `{ "status": "shipped" }` |

Entity fields: `name`; warehouse `address`, `status`; location `warehouse_id`, `status`; item `sku`, `unit_of_measure`, `barcode`. IDs are generated by the server on POST.

Operation example:

```json
{
  "kind": "inbound",
  "warehouse_id": "default",
  "date": "2026-10-18",
  "note": "Opening stock",
  "lines": [{ "item_id": "<item-id>", "location_id": "", "quantity": "12.5" }]
}
```

Kinds are `inbound`, `outbound`, `transfer`, `adjustment`. Quantity is a decimal **string**; negative quantities are permitted only for adjustments. Transfer destinations use `to_warehouse_id` and optional `to_location_id`. Outbound accepts optional `tracking_reference` and initial `status` (default `pending`). Other record kinds are immediately posted. Errors return 400 for invalid inputs, 404 for missing records, and 409 for invalid transitions or insufficient stock.

## Remaining design scope

Checkout completion, order shipments, accepted procurement receipts and completed production runs now post inventory movements atomically with their source operation. See [Operations backend](operations-backend.md). General Affairs integration remains unimplemented. Camera barcode decoding, valuation/GL posting, serial/lot tracking, nested bins, stock-count batches and transfer approvals are not implemented. Lists currently return all rows; server pagination and search remain future work.

Verify with `go test ./...` in `server` and `pnpm build` in `client`.
